All or nothing: transactions and a rollback journal

How a multi-row INSERT that fails halfway leaves no trace, and how the database recovers if the process dies in the middle of writing pages to disk.

Code: internal/storage/tx.go

The problem

A single SQL command can touch several files: the table, every index on it, and sometimes the catalog. If an INSERT of 10 rows hits a duplicate key on row 7, or the power goes out after the table page was written but before the index page was, the database is left inconsistent: an index pointing at a row that doesn't exist, or a row missing from its index.

Dirty pages stay in memory

Every storage operation runs inside a tx. It opens the files it needs lazily, reads pages by number and keeps every page it modifies in a dirty map, without touching the disk. Reads inside the same transaction see the dirty version first.

internal/storage/tx.go
type tx struct {
    db    *DB
    files map[string]*txFile
}

type txFile struct {
    f     *os.File
    pages int            // pages on disk, counting page 0
    size  int            // pages including the ones created in this tx
    dirty map[int][]byte // modified pages, by number
}

That makes rollback free: if anything fails, the transaction just closes its files and the dirty map is garbage collected. Nothing reached the disk, so there is nothing to undo.

Commit in three steps

Writing the dirty pages is where crashes hurt. my_dbms uses a rollback journal, the same idea as SQLite's default mode:

  • 1. Save the originals. Copy the current version of every page about to change into _journal, together with each file's original length and a CRC32 at the end. fsync the journal and the directory.
  • 2. Write the new pages into the table, index and catalog files, and fsync each one.
  • 3. Delete _journal. This is the commit point: the moment the journal disappears, the new state is official.
_journal format (numbers are uvarint)
"MRNJ" | file count |
  per file: name | original page count | saved page count |
            (page number | original 4 KB)... |
crc32 over everything above

Pages created during the transaction (past the original end of the file) are not copied: undoing them is just truncating the file back to its original length. The fsync on the directory matters too, since creating or removing a file is only durable once the directory entry is flushed.

Recovery on open

Open looks for _journal before doing anything else. The CRC32 tells which step the crash happened in:

  • Crash during step 1: the journal is incomplete, the checksum fails, and the data files were never touched. The journal is simply deleted.
  • Crash during step 2: the journal is valid, and the files may hold a mix of old and new pages. Every saved page is written back, every file is truncated to its original size, and the journal is deleted. The database is exactly as it was before the command.
  • Crash after step 3: no journal, the commit is complete.

Because one transaction covers every file a command touches, a row and its index entries always change together. Recovery is also reused at runtime: if step 2 fails with an I/O error, commit runs the same recoverJournal before returning the error.

DDL and its edges

Creating a table or index creates a new file, which the journal can't describe. So CREATE writes the new file first (with fsync) and only then adds the catalog row in a transaction. A crash in between leaves, at worst, a file the catalog doesn't know about. It is never silently overwritten: creating an object with that name fails until someone removes the file. DROP does the opposite order: remove from the catalog, then delete the files.

The design allows many concurrent read transactions but only one writer, since each writer keeps its own private dirty pages. Enforcing that is the caller's job, which is what the TCP server's lock does. A write-ahead log (WAL) would allow readers and a writer at the same time; that and MVCC are natural next steps.
