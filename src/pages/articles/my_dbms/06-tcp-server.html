A TCP server with a JSON-lines protocol and a readers-writer lock

Exposing the database over the network in about 140 lines of Go: one goroutine per connection, a protocol you can test with nc, and why the lock is per command.

Code: cmd/my_dbms/server.go, cmd/my_dbms/main.go

A protocol you can type

With -listen, the same binary that runs the REPL becomes a server. The protocol is deliberately text-based: the client sends one command per line and receives exactly one line of JSON per command. No client library is needed to try it.

nc
$ go run ./cmd/my_dbms -listen localhost:4321
$ nc localhost 4321
→ SELECT nome FROM p WHERE id = 1;
← {"output":"nome\n----\nAna\n(1 linha)","columns":[{"name":"nome","type":"TEXT"}],"rows":[["Ana"]]}
→ DROP TABLE nada;
← {"error":"tabela \"nada\" não existe"}
→
← {}
→ quit
  • output is the same aligned table the REPL prints, so a dumb client can just show it.
  • A SELECT also carries columns and rows so a smarter client (like a web UI) can render its own table. Cells are []*string in Go, so SQL NULL naturally becomes JSON null.
  • An empty line still gets {}, so a client waiting for one response per line never hangs.

One goroutine per connection

serve accepts connections in a loop and hands each one to go s.handle(conn). Each handler wraps the connection in a bufio.Scanner capped at 1 MB per line (so a client can't make the server buffer forever) and a json.Encoder, whose Encode conveniently writes one value followed by a newline.

cmd/my_dbms/server.go
scanner := bufio.NewScanner(conn)
scanner.Buffer(nil, maxLine)   // 1 MB
enc := json.NewEncoder(conn)
for scanner.Scan() {
    line := strings.TrimSpace(scanner.Text())
    var resp response
    switch line {
    case "":
    case "exit", "quit":
        return
    default:
        resp = s.execute(line)
    }
    if err := enc.Encode(resp); err != nil {
        return
    }
}

Shutting down is just closing the listener: Accept returns net.ErrClosed and serve returns nil. The tests use exactly that to start a server on port 0 and stop it cleanly.

Why the lock is per command

All connections share one storage.DB, guarded by a single sync.RWMutex. A SELECT takes the read lock, so many of them run in parallel; any other command takes the write lock and runs alone. That matches the storage's own rule: any number of read transactions, at most one writer.

cmd/my_dbms/server.go
if sel, ok := stmt.(*parser.Select); ok {
    s.mu.RLock()
    r, err := querySelect(s.db, sel)
    s.mu.RUnlock()
    ...
}
s.mu.Lock()
out, err := run(s.db, stmt)
s.mu.Unlock()

The lock wraps the whole command, not each storage call, because UPDATE and DELETE first read the matching rows and then write them. If another writer slipped in between, the second phase would act on rows that no longer look like what the WHERE saw. A per-command lock is coarse, but it is obviously correct, and finer-grained locking (per table, per row) only really makes sense together with MVCC.

One known limit: the lock lives inside a process. Running the REPL and the server on the same data_dir at the same time is not protected. A file lock on the data directory would close that gap.
