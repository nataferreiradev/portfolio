From text to AST: a hand-written lexer and recursive descent parser

How my_dbms turns select nome from p where id=1; into a typed Go value, without parser generators, and how fuzzing keeps it from crashing.

Code: internal/sql/lexer.go, internal/sql/token.go, internal/parser/parser.go, internal/parser/ast.go

The pipeline

Every command goes through the same three stages. The lexer knows nothing about grammar, the parser knows nothing about tables, and only the executor talks to the disk. Each stage has one input type and one output type, which makes them trivial to test in isolation.

flow
"select nome from p where id=1;"
        │  sql.Lex()       string   → []Token
        ▼
[SELECT] [nome] [FROM] [p] [WHERE] [id] [=] [1] [;]
        │  parser.Parse()  []Token  → Statement
        ▼
&Select{Table: "p", Columns: ["nome"],
        Where: &Comparison{ColumnRef{"id"}, "=", Literal{1}}}
        │  execute()       Statement → output
        ▼
nome
----
Ana

The lexer: one switch over runes

Lex walks the input as []rune (so accented identifiers and strings count characters, not bytes) and decides what to do from the current character alone. There is no state machine table: a single switch covers whitespace, strings, symbols, operators and "everything else is a word".

internal/sql/lexer.go
case strings.ContainsRune(operatorChars, r):
    op := string(r)
    if i+1 < len(runes) && operators[op+string(runes[i+1])] {
        op += string(runes[i+1])   // one rune of lookahead: <=, >=, <>
    }
    tokens = append(tokens, Token{Operator, op, start})
    i += len(op)
  • Operators split words: *=<> are boundaries, so id=1 becomes [id] [=] [1] with no whitespace needed.
  • Strings use doubled quotes as escape: 'it''s' is the text it's. There is no backslash escaping, exactly like standard SQL.
  • Words are classified after they are read: keyword map first, then a number regex, then an identifier regex. Keywords are normalized to upper case, so the parser only ever compares against "SELECT".
  • Every token keeps its position, so errors read posição 14: token inválido "@x" instead of a bare failure.

The parser: one method per grammar rule

The parser is recursive descent: each rule of the grammar is a method that consumes its own tokens and calls the methods of its sub-rules. statement() picks the rule by the first token, looking at the second one only when it has to (CREATE TABLE vs. CREATE INDEX).

A handful of tiny helpers make the rules read almost like the grammar itself: accept (consume if it matches), expect (consume or fail), ident, literal, list (a parenthesized, comma-separated list) and names.

Operator precedence for free

Precedence in WHERE is encoded by which method calls which. or is built from and, and and is built from comparisons, so AND binds tighter than OR without any precedence table. Parentheses simply restart at or.

internal/parser/parser.go
func (p *parser) or() (Expr, error)  { return p.logical("OR", p.and) }
func (p *parser) and() (Expr, error) { return p.logical("AND", p.comparison) }

// logical reads "x op x op x ..." and folds it left to right.
func (p *parser) logical(op string, operand func() (Expr, error)) (Expr, error) {
    left, err := operand()
    if err != nil {
        return nil, err
    }
    for p.accept(op) {
        right, err := operand()
        if err != nil {
            return nil, err
        }
        left = &Logical{Op: op, Left: left, Right: right}
    }
    return left, nil
}

The AST as a sealed interface

Each command is a plain struct. They all implement Statement, whose only method is unexported, so no package outside parser can invent a new statement type. The executor then uses a type switch, and adding a command means adding one more case.

internal/parser/ast.go
type Statement interface {
    statement()
}

type Select struct {
    Table   string
    Columns []string // nil means *
    Where   Expr     // nil means every row
}

Fuzzing: "either an AST or an error, never a panic"

A hand-written parser has many index expressions like tokens[p.pos+1], and each is a potential panic. Go's native fuzzing checks one simple property against millions of random inputs: Lex + Parse either return a statement or an error.

go test ./internal/parser -fuzz FuzzParse
f.Fuzz(func(t *testing.T, input string) {
    tokens, err := sql.Lex(input)
    if err != nil {
        return
    }
    stmt, err := Parse(tokens)
    if err == nil && stmt == nil {
        t.Errorf("Parse(%q) without error and without a statement", input)
    }
})

The same technique was later pointed at the storage decoder, and it found real bugs there: overlong uvarint lengths and stray bits in the NULL bitmap were being accepted as valid rows. The failing input lives in testdata/fuzz as a permanent regression test.
