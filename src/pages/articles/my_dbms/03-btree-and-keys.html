A B+tree from scratch, and keys that sort as bytes

How indexes are stored, why the root never moves, and the byte-encoding trick that lets the tree compare keys without knowing column types.

Code: internal/storage/btree.go, internal/storage/key.go, internal/storage/index.go

Shape of the tree

Each index is a B+tree in its own .mari file, built on the same slotted pages as tables. Leaves hold the actual entries in sorted order and are chained by their link field, so a range scan descends once and then just walks sideways. Internal nodes hold key | child page records, and their link points to the rightmost child.

B+tree
                  page 1: root (internal node)
          ┌───────────────────────────────────────────┐
          │ (k1, pg 2) | (k2, pg 3) | link = pg 4     │
          └───────────────────────────────────────────┘
               /                |                \
          < k1 /     >= k1 and < k2 |                 \ >= k2
  ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
  │ leaf  pg 2  │ ───→ │ leaf  pg 3  │ ───→ │ leaf  pg 4  │ ───→ end
  └─────────────┘      └─────────────┘      └─────────────┘

The root is always page 1

Most textbook B+trees create a new root when the old one splits, which means storing the root's location somewhere and updating it. Here the root never moves: when page 1 fills up, its contents are copied into two new pages and page 1 is rewritten as an internal node with a single key. The tree grows from the top, and no metadata has to track where the root is.

Insertion is a short recursive function. It descends to the right leaf, inserts in sorted position and, if the page overflows, splits it in the middle by bytes (not by count, because entries have variable length) and returns the separator key to the parent, which may split in turn.

internal/storage/btree.go
i := childIndex(records, entry)
child := int(childAt(records, link, i))
sep, right, err = t.insertInto(name, child, entry)
if err != nil || right == 0 {
    return nil, 0, err           // child did not split: done
}
// The child split: keys smaller than sep stay in it, and the pointer
// that used to point at it now points at the new right page.
if i == len(records) {
    link = uint32(right)
} else {
    records[i] = internalRecord(nodeKey(records[i]), right)
}
return t.store(name, n, pageInternal, link, slices.Insert(records, i, internalRecord(sep, child)))
  • Deletes never merge pages. A leaf may even become empty. PostgreSQL makes the same trade-off in a regular DELETE, and it keeps the code much simpler.
  • An entry is at most a quarter of a page. That guarantees a full page always splits into two halves that fit, even in internal nodes, which store the key plus 4 bytes.

Keys that sort as bytes

The tree compares entries with bytes.Compare and knows nothing about INT or TEXT. That only works if values are encoded so that byte order equals value order, which the record format does not do (a little-endian int64 sorts wrong, and a length-prefixed text would put 'b' before 'aa').

internal/storage/key.go
NULL  →  00                                       sorts before everything
INT   →  01 | 8 bytes big endian, sign bit flipped
TEXT  →  01 | bytes, each 00 escaped as 00 FF | 00 01

  -1  →  01 7F FF FF FF FF FF FF FF
   0  →  01 80 00 00 00 00 00 00 00
 'a'  →  01 61 00 01
'ab'  →  01 61 62 00 01               'a' < 'ab' because 00 < 62
  • Flipping the sign bit turns two's complement into unsigned order: negatives come first and -1 sits right before 0.
  • The 00 01 terminator is smaller than any continuation, so a prefix sorts before its extensions. Escaping embedded zeros as 00 FF keeps the terminator unambiguous.
  • Multi-column keys are just concatenation. Because every encoded value knows where it ends, ('a', 'bc') and ('ab', 'c') never collide, and "the first N columns equal X" becomes bytes.HasPrefix(entry, X).

Every entry is unique, even in a non-unique index

An index entry is the encoded key followed by the row's 6-byte RID. Two rows with the same name still produce different entries, so the tree never has to handle duplicates, and deleting the entry of a specific row finds exactly that one.

PRIMARY KEY and UNIQUE are enforced by the same index. Before writing a row, the storage seeks the key and checks whether the first entry found starts with it. Keys containing NULL are skipped, because in SQL NULL is not equal to anything, so a UNIQUE column accepts many NULLs.

internal/storage/index.go
c, err := t.btreeSeek(idx.Name, key)   // first entry >= key
if err != nil {
    return err
}
if c.valid() && hasKey(c.entry(), key) {
    return fmt.Errorf("valor duplicado viola a chave %s: ...", idx.Name)
}

Does it pay off?

The project has a benchmark for SELECT ... WHERE id = ? through the primary key index. Growing the table 100× barely moves the time per lookup, which is the logarithmic behavior a B+tree promises (these numbers include lexing, parsing, planning and opening the files):

go test -bench SelectByKey ./cmd/my_dbms
BenchmarkSelectByKey/100      16.2 µs/op
BenchmarkSelectByKey/1000     18.0 µs/op
BenchmarkSelectByKey/10000    19.9 µs/op
