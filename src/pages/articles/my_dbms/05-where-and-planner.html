Three-valued logic and a rule-based query planner

Compiling a WHERE clause into closures, why NULL = NULL is not true, and how the planner decides between a full scan and an index range.

Code: cmd/my_dbms/where.go, cmd/my_dbms/plan.go, internal/storage/index.go

Compile once, run per row

Interpreting the AST for every row would repeat the same work over and over: look up the column index, convert the literal '30' to a number, pick the comparison. compileWhere does all of that once and returns a tree of Go closures. Validation happens at compile time too, so WHERE idade = 'abc' on an INT column fails even on an empty table.

cmd/my_dbms/where.go
type predicate func(row []storage.Value) tri
type getter    func(row []storage.Value) storage.Value

case parser.ColumnRef:
    i := schema.ColumnIndex(e.Name)          // resolved once
    return func(row []storage.Value) storage.Value { return row[i] }, ...
case parser.Literal:
    v, err := literalValue(e, typ)           // converted once
    return func([]storage.Value) storage.Value { return v }, ...

NULL and three-valued logic

In SQL, comparing anything with NULL is neither true nor false: it is unknown. WHERE email = NULL matches no rows, and NOT-style reasoning breaks if you treat unknown as false too early. my_dbms models this with an ordered type where AND is min and OR is max:

cmd/my_dbms/where.go
type tri int

const (
    triFalse tri = iota   // false < unknown < true
    triUnknown
    triTrue
)

if e.Op == "AND" {
    return func(row []storage.Value) tri { return min(left(row), right(row)) }, nil
}
return func(row []storage.Value) tri { return max(left(row), right(row)) }, nil

unknown AND false is false, unknown OR true is true, and the WHERE only keeps rows that evaluate to exactly triTrue. Go 1.21's built-in min and max make the whole truth table two lines long. To test for missing values you use IS NULL, which is the only operator that looks at the null flag directly.

Choosing a plan

choosePlan decides how SELECT, UPDATE and DELETE read rows. It has no statistics; it is a small rule-based planner that only looks at column op literal comparisons joined by AND at the top level of the WHERE. Anything under an OR is ignored, because a row could match through the side the index doesn't cover.

  • An index on (a, b, c) is usable when the WHERE fixes a prefix of its columns with = and, optionally, bounds the next column with <, <=, > or >=.
  • Scoring: each equality is worth 2 points and a range is worth 1. The highest score wins; ties go to the first index of the table, which is the primary key.
  • 5 < id is normalized to id > 5 with a small flip map, so literal-on-the-left still uses the index.
  • No usable index means a full scan.
EXPLAIN
my_dbms> CREATE INDEX p_idade ON p (idade);
my_dbms> EXPLAIN SELECT * FROM p WHERE idade >= 30 AND idade < 40 AND nome <> 'x';
busca no índice p_idade da tabela p (idade >= 30 AND idade < 40)

my_dbms> EXPLAIN SELECT * FROM p WHERE idade = 30 OR id = 1;
varredura completa na tabela p

The index is only a coarse filter

The plan becomes a storage.IndexRange: the equality values for the leading columns plus optional From/To bounds for the next one. The storage encodes them with the same byte-sortable key format, seeks to the start and walks the leaves until an entry no longer has the prefix or passes the end key.

Bounds are inclusive and the index may return a few extra rows (rows with NULL, or id = 5 for id > 5). That's fine by design: the full compiled WHERE still runs on every row the index returns. Keeping the index as a pre-filter means the planner can never change a query's result, only its speed.

cmd/my_dbms/plan.go
func (p plan) rows(db *storage.DB) iter.Seq2[storage.Row, error] {
    if p.index == nil {
        return db.Scan(p.table)
    }
    return db.IndexScan(p.table, p.index.Name, p.r)
}

for row, err := range plan.rows(db) {   // Go 1.23 range-over-func
    ...
    if where(row.Values) == triTrue { ... }
}

Both access paths are iter.Seq2 iterators, so the executor doesn't care which one it got, rows are streamed instead of loaded into a slice, and breaking out of the loop stops the scan and closes the transaction through defer.
