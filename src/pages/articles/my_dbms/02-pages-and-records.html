Slotted pages and stable row ids: the on-disk format

Why the project moved from CSV files to fixed-size pages, how a row becomes bytes, and why a deleted row leaves a hole instead of shifting its neighbors.

Code: internal/storage/page.go, internal/storage/heap.go

Why pages

Early versions stored each table as a CSV file. It is easy to read, but every write rewrote the whole file, and there was no way to point at "row 42" without scanning. Databases like SQLite and PostgreSQL solve this by splitting files into fixed-size pages: page N starts at byte N × page_size, so reading one page is a single ReadAt, and a write touches only the pages that changed.

Page 0 of every .mari file is a header: the magic MRNA, a format version and the page size. Opening a file with a different page size, or an old CSV file, fails loudly instead of returning garbage.

Anatomy of a slotted page

Records have variable length, so a page can't be an array of fixed cells. Instead, a small slot array grows from the start of the page and the records grow from the end. Each slot is 4 bytes (offset and length), and the page is full when the two meet in the middle.

layout
page N
┌──────────────────────────────────────────────────────────────┐
│ kind | – | slot count | records start | link | slot 0 …     │  slots grow →
│                                                              │
│                        free space                            │
│                                                              │
│                      … | record 1 | record 0                 │  ← records grow
└──────────────────────────────────────────────────────────────┘
header: 10 bytes, little endian       slot: offset (u16) + size (u16)

The kind byte tells what the page holds: heap records (1), a B+tree leaf (2) or a B+tree internal node (3). Tables and indexes share the exact same page code, which kept the B+tree implementation small. Since offsets are uint16, pages top out at 32 KB; the default is 4 KB, configurable in my_dbms.conf.

A row in bytes

A record is a NULL bitmap followed by the non-NULL values, guided by the column types. INT is a fixed 8-byte int64; TEXT is a uvarint length followed by the raw bytes. Because the length comes first, there is no escaping at all: a text can contain commas, quotes or newlines, which was a constant headache in the CSV days.

record encoding
-- pessoas (id INT, nome TEXT, email TEXT)
INSERT INTO pessoas VALUES (1, 'Ana', NULL);

04                          NULL bitmap 0000_0100: column 2 (email) is NULL
01 00 00 00 00 00 00 00     id = 1   (int64, little endian)
03 41 6E 61                 nome = "Ana"  (uvarint length 3 + bytes)
                            email takes no space at all

A record must fit in an empty page: at most page_size − 14 bytes (page header plus one slot). Larger rows are rejected with an error before anything is written. Overflow pages, like PostgreSQL's TOAST, are a possible future step.

RID: an address that must not move

Each row has a RID (row id): the pair (page, slot), like PostgreSQL's ctid. Indexes store RIDs to find rows, so the code goes out of its way to keep them stable:

  • DELETE doesn't repack the page. It marks the slot as dead (length 0); the record's bytes become a hole.
  • UPDATE rewrites the record in the same slot. Only if the new version doesn't fit, even after reclaiming holes, does the row move to another page and get a new RID (and every index is updated in the same transaction).
  • Compaction slides records together to merge the holes, but keeps slot numbers untouched. Only the offsets inside the slots change.
  • INSERT reuses a dead slot when it finds one, and only tries the last page. A free space map is on the to-do list.

The catalog is just another table

The schema itself lives in _catalog.mari, stored in the same format as user tables, with one row per object and a type column as discriminator (table, primary_key, unique, index). Since the catalog's own schema is hard-coded, it can be read with plain SQL: SELECT * FROM _catalog;. Three more system tables, _settings, _tables and _indexes, are not on disk at all: their rows are built in memory from the database state, like PostgreSQL's pg_settings views.

REPL
my_dbms> SELECT * FROM _catalog;
type        | name              | table_name | definition
------------+-------------------+------------+--------------------------------------
table       | pessoas           | pessoas    | id INT NOT NULL,email TEXT,nome TEXT
primary_key | pessoas_pkey      | pessoas    | id
unique      | pessoas_email_key | pessoas    | email
index       | pessoas_nome      | pessoas    | nome
